## 1. 한 줄 소개
경고등이 켜지기 전, 운전자가 느낀 **이상 증상**을 간단히 선택·입력받아 차량 상태·부품 수명·정비 이력을 함께 따져 **"안 가도 되는 것 / 간단히 고칠 것 / 센터에 갈 것 / 지금 멈출 것"**을 구분해 주고, 센터에 갈 때는 **사전 진단서**로 대기와 헛걸음을 줄이는 차량 내 예방정비 서비스

## 2. 문제 정의

### 2-1. 핵심 문제: "이상한데, 어느 정도로 심각한지 모른다"
운전자는 이상을 느껴도 선택지가 극단적이다.
- **무시하고 계속 운행** → 작은 문제가 커지거나 안전 위험
- **일단 센터 예약** → 퓨즈 하나, 공기압 하나로 해결될 일에도 시간·비용 소모

중간 판단(이건 간단히 해결, 이건 점검 필요, 이건 즉시 정차)을 도와주는 수단이 차 안에 없다.

### 2-2. 문제의 원인 구조
| 원인 | 설명 |
|---|---|
| 정보 부족 | 증상과 부품의 관계, 긴급도를 운전자가 알기 어렵다 |
| 수명 관리 공백 | 소모성 부품은 문제가 없으면 교체하지 않아 권장 주기를 넘기기 쉽고, 반대로 주기 전에 고장나기도 한다 |
| 이력 단절 | 정비가 현대 서비스·사설로 나뉘어 내 차의 부품 상태를 스스로 알기 어렵다 |
| 센터 운영 비효율 | 증상·상태를 모른 채 접수하면 경정비/중정비 구분, 정비사 배치, 부품 준비가 늦어진다 |

### 2-3. 기존 서비스의 빈틈 (확인한 범위에서)
| 구분 | 내용 | 출처 |
|---|---|---|
| 블루링크 차량 진단 | 엔진·변속기 계통, **경고등이 켜진 경우** 중심. 결과는 원격 신호 기준 1차 판단, 이후 상담원·센터 연결 | 현대차 공식 페이지, 취급설명서 |
| 리모트 케어(선제케어) | 원격 확인 가능한 데이터에 한해 이상 감지. 현재 전기·수소차 7개 차종, 블루링크 가입 고객 한정 | 현대차 공식 페이지 |
| 정비 예약 | 차량 화면의 QR로 폰 앱(마이현대)으로 이동해 예약 | 취급설명서 |

## 4. 서비스 개요

### 4-1. 핵심 개념: 4단계 트리아지 (Triage)
이 서비스의 핵심은 "무조건 센터로 보내는 것"이 아니라 **증상에 맞는 조치 수준을 구분**하는 것이다.

| 단계 | 의미 | 안내 방향 | 예 |
|---|---|---|---|
| **1. 즉시 정차** | 안전 위험이 높음 | 안전한 곳에 정차, 견인·긴급 출동·센터 연결 | 브레이크 이상, 냉각수 과열, 빨간 경고등 |
| **2. 센터 점검** | 전문 점검이 필요하나 즉시 위험은 아님 | 기간 내 입고 권유, 사전 진단서 전달, 예약 | 점화 계통 열화 의심, 브레이크 패드 마모 |
| **3. 간단 조치** | 운전자가 정차 후 직접 해결 가능 | 단계별 안내, 필요 부품 안내, 해결 안 되면 센터로 | 퓨즈, 와이퍼, 전구, 공기압, 워셔액 |
| **4. 경과 관찰** | 즉각 조치 불필요 | 모니터링, 재확인 시점 안내 | 일시적 현상, 환경 요인 |

판단 기준은 3개 축이다.
1. **안전 위험도** (계속 운행해도 되는가)
2. **조치 난이도** (운전자 직접 / 센터)
3. **확신도** (증상·데이터가 얼마나 분명한가) → 낮으면 추가 질문, 그래도 불명확하면 **보수적으로 상위 단계**로 안내

### 4-2. 핵심 가치
1. **경고등 이전**에 이상을 짚는다 (증상 + 차량 데이터)
2. **부품 수명·주행거리·내 교체 이력**으로 개인화된 예방정비 시점을 안내한다
3. **불필요한 센터 방문은 줄이고, 필요한 방문은 빠르게** 만든다 (간단 조치 안내 + 사전 진단서)

### 4-3. 왜 "차 안"인가 (폰 앱이 아닌 이유)
- **이상을 느낀 바로 그 순간**에 쓸 수 있다 (진동·소음은 운전 중에 발생)
- 주행거리·경고등·오일류·타이어압 등 **차량 데이터를 자동으로 함께 판단**한다
- **정차 상태**(출발 전 시동 시점, 안전한 곳에 세운 뒤)에서 증상을 선택해 바로 점검한다. **주행 중에는 조작을 요구하지 않고** 안전 정차 안내만 한다 (4-5 참고). `[차량 UX·주행 중 조작 가이드 확인 필요]`
- 음성 접수는 이상적인 방식이나 현재 음성 SDK(STT/TTS)가 준비 중이므로 **SDK 공개 시 확장**한다 (로드맵)
- 센터 길 안내가 **같은 흐름**에서 이어진다

### 4-4. 사전 진단서(접수 카드) 구성
- 증상(운전자 설명), 발생 상황(정차/가속/고속 등)
- 차량 데이터 스냅샷 (주행거리, 타이어 저압 경고, 램프·와이퍼·윈도우 등 상태, EV 배터리 잔량 등 **차량이 제공하는 범위**. 지원 여부는 `checkCapabilities`로 확인하고 미지원 항목은 제외)
- 의심 부품 후보와 교체 이력, 권장 주기 대비 상태
- 트리아지 단계, **예상 작업 난이도(경정비/중정비)**
- ※ 진단서는 정비사 **참고 자료**이며 센터에서 재점검한다.

### 4-5. 사용 상황별 흐름 (주행 상태 게이트)
증상을 느끼는 상황이 다르면 앱의 동작도 달라야 한다. **차량이 움직이는 동안에는 점검 조작을 하지 않는 것**이 원칙이다.

| 상황 | 앱의 동작 |
|---|---|
| **① 출발 전 (시동 직후, 정차)** | 바로 증상을 선택해 점검을 진행한다. "시동 걸 때 떨림·소음"은 이 상황에서 가장 자주 나타나며, 시나리오 A가 해당한다. |
| **② 주행 중 이상 감지·느낌** | **조작을 요구하지 않는다.** "안전한 곳에 정차해 주세요"라는 짧은 안내만 표시한다. 필요하면 큰 버튼 하나로 "이상 증상 있음"만 표시해 둔다. |
| **③ 안전하게 정차한 뒤** | "아까 느낀 이상을 확인할까요?"라고 묻고, 증상 선택 → 점검(①과 동일)으로 이어진다. |
| **④ 위험 증상·경고등(주행 중)** | 즉시 정차 안내(트리아지 1단계)와 긴급 연결을 우선한다. 점검 흐름으로 넘기지 않는다. |

- 정차 여부 판단: Vehicle SDK에는 속도·기어가 없어 **Android Automotive 표준 주행 상태 정보**를 쓴다. 에뮬레이터에서 **기어(P 등)와 주차 브레이크는 읽기·구독이 확인**되었고 속도는 권한 문제로 읽을 수 없다(8장). 정차 기준은 "선택 기어 P"(주차 브레이크는 보조). Virtual Console에서 P↔D 변경 시 값·이벤트 변화 확인(2026-11-08). (위치 SDK인 FusedLocation은 Playground 콘솔에서 "Coming Soon", 2026-10-24)
- **플랫폼의 주행 중 제한 (2026-11-08 에뮬레이터 확인)**: 기어가 D이면 Pleos Connect 차량 화면이 앱 실행 자체를 막고 **"주행 중에는 사용할 수 없습니다."** 를 표시한다(P로 바꾸면 앱이 열림). 즉 "주행 중 조작을 요구하지 않는다"는 원칙은 플랫폼이 이미 강제하며, 우리 앱의 역할은 **정차한 뒤 증상 접수를 이어주는 것**이다. 주행 중 "정차해 주세요" 안내를 앱 화면으로 띄울 수 있는지(알림·음성 등)는 확인 전이므로 단정하지 않는다. `[확인 필요: 주행 중 알림 가능 범위]`
- 데모에서는 실제 기어 값을 쓰되, 이상·주행 중 상황은 **"주행 중/정차 중" 상태를 시뮬레이션**하여 게이트 동작을 보여준다.
- Android Automotive는 일반적으로 주행 중 UI 조작을 제한하는 체계를 갖고 있으므로 Pleos 환경에서의 규정과 맞춰 설계한다. `[Pleos 디자인·UX 가이드 확인 필요]`

## 5. 사용자 시나리오 (대표 3개)

> 시나리오는 **에뮬레이터에서 실제로 지원이 확인된 차량 데이터**를 근거로 구성했다 (검증 결과: `에뮬레이터_검증결과.md`). 확인되지 않은 부분은 `[검증 필요]`로 표시한다.

**시나리오 A. 간단 조치: 기능 하나만 이상 → 전구·퓨즈 점검** (상황 ①·③: 정차 상태)
1. 증상 선택: [기능 이상] → [전조등 / 와이퍼 / 윈도우 등] (다른 기능은 정상)
2. 앱이 선택지로 추가 질문한다: 그 기능만? 한쪽만 안 되는가? 다른 전기 장치는 정상?
3. 앱이 해당 기능의 **조작(스위치) 값과 실제 상태 값**을 조회해 **보조 근거**로 쓴다. 에뮬레이터 기본값에서도 하이빔은 스위치 OFF·상태 ON처럼 **정상일 때 두 값이 다를 수 있음**이 확인되어, 불일치만으로 고장을 단정하지 않고 **운전자 선택과 함께** 판단한다. `[램프별 의미 검증 필요, 고장 상황은 모의 데이터로 시연]`
4. 불일치 또는 단일 기능 이상이면 "전구 또는 퓨즈 이상일 수 있어요"로 안내하고, 정차·시동 off 상태에서 확인할 **퓨즈박스 위치, 같은 용량 부품 사용, 교체 단계**를 보여준다.
5. 교체 후에도 반복되면 배선 문제일 수 있어 센터로 연결한다. (시나리오 B와 동일 흐름)
- 근거 데이터: Light, Wiper, Window, Door의 상태(READ)와 스위치(READ_WRITE) 지원 확인

**시나리오 B. 센터 점검: 증상 + 주행거리 기반 예방 점검** (상황 ①: 출발 전 시동 직후, 정차 중)
1. 증상 선택: [진동·떨림] → [시동 걸 때] + [가속이 둔함] (경고등 없음)
2. 앱이 선택지로 추가 질문한다: 언제부터? 정차 중에도? 소리도 나는가?
3. **현재 주행거리를 조회**하고(지원·읽기 확인), 사용자가 입력한 **부품별 교체 이력**과 권장 주기를 비교한다. `[이력은 사용자 입력·모의 데이터]`
4. "마지막 교체 후 N km, 권장 주기 초과 가능성" → 점검 후보와 긴급도 안내. "다른 원인도 가능해요. 2주 내 점검을 권해요."
5. **사전 진단서**를 생성하고 가까운 서비스센터로 안내한다.
- 부품 후보는 **파워트레인별**로 다르다. (내연기관: 점화 계통 등 / 전기차: 12V 배터리, 브레이크 패드, 타이어 등) 시연 차량(전기차)에서는 내연기관 부품의 실제 데이터를 시연할 수 없으므로, 해당 항목은 **차종 지원 시 동작하는 구조**로 설명한다.
- 근거 데이터: Odometer(현재 주행거리) 읽기·구독 확인

**시나리오 C. 즉시 정차 후 조치: 타이어 저압** (상황 ②→③: 주행 중 감지 → 정차 후 확인)
1. 주행 중 **타이어 저압 경고**를 감지하면 조작 요구 없이 **"안전한 곳에 정차해 주세요"** 표시
2. 정차를 확인한 뒤 어느 바퀴인지 확인한다. (바퀴 4개 영역 읽기는 확인됨. 단 읽힌 값 137.0이 **임계값인지 현재 압력인지 의미 미확인** `[검증 필요]`)
3. 공기압 보충으로 해결 가능한 경우 **간단 조치**(주유소·정비소 공기압 보충 안내), 급격한 저하·손상이 의심되면 **견인·센터 연결**
- 근거 데이터: Tire 저압 경고(READ) 지원 확인
- **위험 증상 선택**: 운전자가 [브레이크가 물렁함] 같은 위험 증상을 선택하면 데이터와 무관하게 즉시 정차 안내 + 긴급 연결(트리아지 1단계). 브레이크액 등 차량 데이터는 에뮬레이터에서 미지원이므로 **운전자 선택 기반**으로 동작한다.
- 주행 중 증상을 운전자가 먼저 느낀 경우는 상황 ②처럼 안전 정차 안내만 하고, 정차 후 ③에서 점검을 이어간다.

## 6. 증상–부품 사례 카탈로그 (예시, 확장 가능)
> 일반 정비 상식 기반. 부품 후보는 "확률적 후보"이며 확정 진단이 아니다. 차종·파워트레인별로 검증 필요.

| 증상 | 의심 후보(예) | 조치 수준 | 활용 데이터 | 에뮬레이터 검증 |
|---|---|---|---|---|
| 시동 시 떨림, 가속 둔함, 연비 저하 | 점화플러그, 점화코일, 흡기·연료 계통 | 센터 점검 | Odometer + 교체 이력(입력) | 주행거리 읽기 **확인**, 이력은 모의. 내연기관 부품 데이터는 EV 에뮬레이터에서 시연 불가 |
| 특정 기능만 안 됨(카메라, 시거잭, 한쪽 창문 등) | **퓨즈** | **간단 조치** | Light·Wiper·Window·Door 상태 vs 스위치 | 지원 **확인**, 불일치 재현은 `[미검증]` |
| 한쪽 전조등·방향지시등 안 켜짐, 깜빡임이 빠름 | 전구(램프) | 간단 조치(차종에 따라 센터) | Light 상태, TurnSignal | 지원 **확인**, 좌우 구분은 `[미검증]` |
| 와이퍼 줄무늬·떨림 소리 | 와이퍼 블레이드 | 간단 조치 | Wiper 상태·스위치 | 지원 **확인** (줄무늬는 데이터로 감지 불가, 운전자 선택 기반) |
| 핸들 쏠림·고속 진동 | 타이어 공기압(간단), 휠 밸런스·얼라인먼트(센터) | 간단 조치 / 센터 | Tire 저압 경고, SteeringWheel | 저압 경고 지원 **확인**, 바퀴별 값 읽기 `[미검증]` |
| 워셔액 경고 | 워셔액 부족 | 간단 조치 | Safety(워셔액) | **미지원** → 운전자 선택·계기판 표시 기반 |
| 에어컨 풍량 약함·냄새 | 에어컨(캐빈) 필터 | 간단 조치 / 센터 | HVAC 상태 + 주행거리·이력 | HVAC 지원 **확인** (필터 상태 자체는 데이터 없음) |
| 시동 시 힘없이 걸림, 전자장치 오작동 | 12V 배터리 | 센터(또는 출장) | 사용 기간·이력 | 12V 배터리 데이터 **없음** (EV 배터리 잔량은 고전압용) |
| 브레이크 소음·페달 떨림 | 브레이크 패드·디스크 | 센터 점검 | Brake 페달 상태 | 페달 상태 지원 **확인**, 브레이크액 **미지원** |
| 엔진오일 부족·교환 시점 | 엔진오일 | 센터 | Safety(오일) | **미지원**(EV) → 차종 지원 시 동작 |
| 냉각수 과열, 빨간 경고등, 브레이크가 물렁함 | 냉각·제동 계통 | **즉시 정차** | 운전자 선택 + 경고등(Telltale) | 경고등 API는 샘플에서 차단됨 → **운전자 선택 기반**, 사용 가능 여부 주최 측 확인 |

- 전기차는 점화 계통이 없으므로 부품군을 **파워트레인별로 분리**한다. (예: 전기차는 12V 배터리, 타이어, 와이퍼, 필터 등)
- 사례 데이터는 **규칙 기반 DB**로 구성해 항목을 쉽게 추가할 수 있게 한다.
- 데이터가 없는 항목은 **운전자 선택 + 주행거리·이력 규칙**으로 판단하고, 차종이 해당 데이터를 제공하면 `checkCapabilities`로 자동 활용한다.

| SDK | 사용 목적 |
|---|---|
| Vehicle SDK – Odometer | 현재 주행거리 읽기·구독 → 부품 수명 계산 (**에뮬레이터 읽기 확인**) |

| Vehicle SDK – Brake / TurnSignal / SteeringWheel / Seat / HVAC / EV battery | 증상 관련 상태·맥락 조회 (지원 확인) |
| Vehicle SDK – Safety (경고등·오일류) | **차종 지원 시 활용**. 에뮬레이터(EV)에서는 오일·브레이크액·워셔액 미지원, 경고등(Telltales) API는 샘플에서 차단되어 `[주최 측 확인 필요]` |
| SpeechToText / TextToSpeech | **로드맵**: 음성 접수·결과 안내 (Playground 콘솔에서 "Coming Soon"으로 확인, 2026-10-24) |
| NaviHelper SDK | 서비스센터 경로 안내 |
- 기능 지원 여부는 `checkXXXCapabilities`로 확인하고, 미지원 시 대체 흐름으로 동작한다.
- **권한 방식 (운영사무국 회신)**: Connect SDK 문서가 안내한 user permission을 AndroidManifest에 선언하면 **에뮬레이터 개발·테스트에는 별도 권한 신청·승인이 필요하지 않다.** 앱마켓 배포는 **별도 권한 심사**를 받으며, 실차 테스트나 빠른 승인은 보장되지 않는다. 본 기획서의 시연·검증은 모두 **지정 에뮬레이터 기준**이다.
- 최소 권한 원칙: 서비스에 필요한 퍼미션만 선언한다(읽기 중심: 주행거리·타이어·램프·와이퍼·윈도우·도어 등). 제어(CONTROL_*) 권한과 Vehicle Control SDK(준비 중)는 사용하지 않는다. 공식 샘플 앱 매니페스트에는 `CAR_SPEED`·`CAR_DRIVE` 등 주행 관련 읽기 권한도 선언돼 있어 주행 상태 판단에 쓸 수 있는지 검증한다. `[검증 필요]`
- 개별 Vehicle API(Telltales·TirePressure 등)와 참가자 사용 범위는 운영사무국이 42dot에 **확인 중**이다. 확정 전까지 해당 API에 의존하지 않는다.
- **개발 도구·심사 기준 (운영사무국 회신)**: 생성형 AI 등 개발 보조도구 사용 가능. 단 출품작은 Pleos 개발환경에서 개발·검증해 **지정 에뮬레이터에서 앱과 주요 기능이 정상 동작**해야 하며, 2차 PT에서 **참가자가 코드의 동작 원리를 직접 설명**한다. 이에 따라 코드는 작게(규칙표 JSON + 화면 3~4개) 유지한다.
- **에뮬레이터 검증 요약 (2026-10-24, Pleos_Connect v2.1.0 / Vehicle SDK 2.3.2)**: 19개 도메인의 지원 확인 요청 116건 중 **82건 지원, 34건 미지원**. 미지원은 연료 계열 전부, 트립(주행시간·거리) 8건, 오일·브레이크액·워셔액, 전비 등이다. (상세: `에뮬레이터_검증결과.md`)
- 이 결과를 반영해 시연 시나리오는 **지원이 확인된 데이터**(주행거리, 램프·와이퍼·윈도우, 타이어 저압 경고)를 근거로 구성했고, 미지원 항목은 **운전자 선택 + 이력 규칙**으로 대체하되 차종이 지원하면 자동 활용한다.
- **값 읽기 검증(2026-10-24)**: Light(상태·스위치), Wiper, Window, Door, Seat(점유·벨트), Tire(바퀴 4개), Odometer, EV 배터리, 조향각, 방향지시등, 브레이크 페달은 에뮬레이터에서 **실제 값이 읽힘**. 영역 일부는 "area not supported"로 실패하므로 앱은 영역별 성공 여부에 따라 동작해야 함.
- **한계**: 램프 스위치와 상태가 정상일 때도 다를 수 있고(하이빔 스위치 OFF·상태 ON), 에뮬레이터는 전구 고장 같은 이상 상황을 만들지 못함. 따라서 차량 데이터는 **보조 근거**, 판단의 중심은 **운전자 선택 + 주행거리·이력 규칙**으로 설계한다.
- `[검증 필요]` 타이어 `getLowTirePressure` 값(137.0)의 의미.
- **주행 상태(정차 여부) 판단 (2026-11-07 에뮬레이터 검증)**: Vehicle SDK 도메인에는 기어·속도가 없으나, Android Automotive 표준 `CarPropertyManager`로 **기어(P/R/N/D)와 주차 브레이크는 읽혔고 변경 구독도 가능**했다. 속도는 `CAR_SPEED` 권한이 앱에 부여되지 않아 읽을 수 없다. Virtual Console로 기어를 P↔D로 바꾸면 `GEAR_SELECTION` 값과 변경 이벤트가 실제로 바뀌는 것을 확인했다(`CURRENT_GEAR`는 속도 0이라 P에 머묾). 따라서 정차 판단은 **"선택 기어가 P"** 를 기준으로 하고 주차 브레이크는 보조로 쓴다. `[실차·앱마켓 배포 시 권한은 주최 측 확인 필요]`

## 9. 판단 로직과 신뢰성 (논리 보강)

### 9-1. 판단 흐름
증상 선택 → 선택지 추가 질문(확신도 향상) → 차량 데이터·수명·이력 조회 → 후보 부품 도출 → 위험도·난이도 평가 → 트리아지 단계와 근거 안내

### 9-2. 오판 대비 원칙
| 오류 유형 | 위험 | 대응 |
|---|---|---|
| 위험한데 가볍게 안내(과소 판정) | 안전 사고 | 위험 신호는 **무조건 상위 단계**, 불확실하면 보수적으로 상향 |
| 가벼운데 센터 권유(과대 판정) | 불필요 방문 | 허용(안전 우선), 센터 재점검으로 보정 |
| 후보 부품이 틀림 | 신뢰 저하 | "후보"와 "다른 원인 가능성"을 함께 안내, 센터에서 재점검 |
- 결과는 **확정 진단이 아닌 참고 안내**로 표현한다.
- 간단 조치 안내는 **정차·시동 off 상태**에서만, 해결되지 않거나 반복되면 센터로 안내한다.
- 목표 지표: 과소 판정 최소화(시나리오 테스트에서 위험 케이스 100% 상향 안내) `[테스트 설계 필요]`

### 9-3. 개인정보·동의
- 증상, 차량 데이터, 위치를 센터에 보낼 때 **제공 동의** 절차를 거친다.
- 최소 수집, 목적 한정, 사용자가 전송 내용을 확인 후 보내는 구조.

| 판단 | 센터 연결이 목적지 | **4단계 구분: 안 가도 되는 것과 가야 하는 것을 가름** |
| 개인화 | 일반 안내 | **부품 수명·주행거리·내 이력 반영** |
| 흐름 | 차 → 폰 앱으로 이동하여 예약 | **차 안에서 진단서·센터 안내까지 한 흐름** |
- 블루링크 진단과 **경쟁이 아닌 보완**: 앞단(증상 접수·1차 판단)과 뒷단(센터·조치 연결)을 맡고, 경고등이 켜지면 기존 진단으로 연결한다.

## 11. 사업성

### 11-1. 가치 구조
| 주체 | 가치 |
|---|---|
| 운전자 | 고장 예방, 불안 해소, **불필요한 센터 방문·비용 감소**, 방문 전 상태 파악 |
| 서비스센터 | 경정비/중정비 사전 구분, 정비사 배치, 부품 사전 준비, 예약 슬롯 산정, **간단 조치로 해결될 방문 감소 → 중정비 여력 확보** |
| 현대차 | 이탈 고객 재유입 유도, 정비 이력 데이터 확보, 고객 신뢰·만족 |

### 11-2. 예상되는 반론과 답변
**Q. 간단 조치를 안내하면 센터 매출이 줄지 않나?**
- 센터 수용력은 한정되어 있고 대기가 문제다. 불필요한 방문이 줄면 중정비·예방정비에 자원을 집중할 수 있다. `[가설, 검증 필요]`
- "무조건 센터로 보내는" 서비스보다 **신뢰**를 얻어 장기 재방문(예방정비 입고)으로 이어질 것으로 본다.

**Q. 사설 정비로 가는 고객은 어떻게 되나?**
- 정비 이력을 **영수증 사진·간단 입력**으로 받아 현대/사설 구분 없이 기록한다. 이력 때문에 현대 서비스를 써야 하는 구조가 아니다.
- 사전 진단서가 대기·헛걸음을 줄이면 센터 이용의 불편 요소 일부가 완화된다. (정비 단가 자체는 본 서비스 범위 밖)

**Q. 블루링크·마이현대와 중복 아닌가?**
- 경고등 이후/센터 연결 중심의 기존 서비스 **앞단**을 맡고, 연결은 기존 서비스로 이어진다. `[마이현대 앱 확인 후 보정]`

### 11-3. 성과 지표 (제안)
- 이용자: 월 이용자(MAU), 증상 접수 후 조치 이행률, 재이용률
- 서비스: 예방점검 예약 전환율, **간단 조치 완료율**, 사전 진단서 기반 입고 건수
- 센터: 진단서 사용 건의 예약 소요 시간·헛걸음 비율
- 예상 MAU·리텐션 `[대상 차량 수·이용률 가정 설정 후 산출]`
- 리텐션 요인: 주행거리 구간별 점검 알림, 이력 누적

### 11-4. 한계 인식
- 서비스센터 예약·배정 시스템은 현대차 내부 시스템이므로, 본 공모전에서는 **연동 구조 제안과 모의 화면**으로 제시한다.
- 부품 수명 판단의 정확도는 이력 데이터 품질에 의존한다.

## 15. 미확인·확인 필요 사항
- **Telltales(경고등)·TirePressure(공기압 값) API**: 공식 샘플이 차단한 API. 공모전 참가자의 사용 가능 여부를 주최 측에 확인
- **명령-상태 불일치 재현**(램프·와이퍼·윈도우), **타이어 바퀴별 값 읽기**, **주행 상태(기어·주차 브레이크·속도) 읽기**: 샘플 앱에 읽기 코드를 추가해 검증
- **주행거리 값 주입**: 시연용으로 0이 아닌 주행거리를 에뮬레이터에 넣는 방법
- **음성 SDK(STT/TTS) 상태**: 문서상 "준비 중". 공개 시기, 대체 수단(Android 표준 음성 기능) 확인
- 주행 중 터치 조작 제한 등 **차량 UX 가이드** (Pleos 디자인 가이드 확인)
- 마이현대 앱 소모품·정비 기능과의 겹침 범위
- 에뮬레이터에서 Odometer·Safety·Tire·Light·Wiper 등 값 지원 여부
- **운영사무국 회신 대기 중** (1·2차 회신에서 "확인 중", 추후 메일 안내 예정): 마이크 원본 음성·센서(가속도·진동) 접근, 음성 처리가 STT/TTS SDK로만 가능한지, DTC 조회 API, 참가자용 Vehicle SDK 도메인·퍼미션 범위, 외부 OBD 어댑터 허용, 대상 차량(신규 출시 차량 기준 여부), 기출고 차량 OTA 계획
